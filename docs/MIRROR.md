# Experimental Mac-to-TV video over DLNA

The UN40FH5303 advertised a DLNA/AllShare `MediaRenderer`, `AVTransport` and
`ConnectionManager` on the home network on 2026-10-25. Its reported sink
formats include MP4 and `AVC_TS_MP_HD_AAC_ISO` (H.264/AAC in MPEG-TS).
Subsequent tests showed that the TV requested and reported playing both a live
test pattern and a Mac screen capture. **The user reported a gray screen,
not the Mac desktop**. Investigation reproduced solid-gray frames in the old
screen MPEG-TS locally. `-b:v 1800k` turned the whole stream gray; retaining
the old `-maxrate`/`-bufsize` with CRF still turned it gray after the first
second. The corrected encoder uses CRF without those bitrate caps; a sustained
local decode now contains nonuniform desktop frames throughout. A native
ScreenCaptureKit helper also supplies Mac system audio instead of the silent
test track when `--system-audio` is selected. After the TV returned to the
LAN, it requested the corrected stream and reported playback; **nobody
confirmed its picture or sound on the panel**.

This is not AirPlay, a Smart Hub replacement or a way to update Netflix,
Prime Video or YouTube.

`tools/dlna_mirror.py` uses the TV's existing DLNA receiver, not an Orsay
widget. It discovers the TV's current control URLs rather than assuming fixed
ports. The tool does not change TV playback without `--play`; screen capture
also requires `--source screen --allow-screen-recording`; system audio requires
the separate `--system-audio` opt-in. For audio, the Mac needs ScreenCaptureKit
(macOS) and `swiftc` from Apple's developer tools; the helper is compiled in a
temporary directory, not installed on the TV. No firmware changes or additional
TV apps are needed for this experiment.

## Read-only check

Run from this project's directory on the Mac:

```bash
python3 tools/dlna_mirror.py --tv 192.168.1.103
```

This discovers the renderer and asks which formats it accepts. It does not
start playback or capture the Mac screen. Replace the IP if the TV's network
address has changed.

## Test with the TV present

**These commands change what's playing on the TV.** Run them only while you
are watching the TV and agree to interrupt its current content.

First try a finite video so that live streaming is not confused with basic
DLNA playback. The existing Orsay Lab server must be running on the Mac at
`192.168.1.102:80`, with `media/test.mp4` generated by
`python3 tools/make_sample.py`:

```bash
python3 tools/dlna_mirror.py --tv 192.168.1.103 \
  --sample-url http://192.168.1.102/media/test.mp4 --play
```

Confirm **both picture and sound by looking at the TV**. The previous widget
test only received a playback-complete event; it did not confirm either.
The TV may ask to allow the Mac as a media device. For F-series sets,
[AirBeamTV's instructions](https://www.airbeam.tv/knowledge-base/the-first-time-that-i-use-screen-mirroring-on-my-samsung-tv-should-i-allow-the-incoming-connection-on-tv/)
identify Menu > Network > AllShare Settings > Content Sharing as the place to
review a connection that was denied.

If the finite MP4 works, test live playback **without** capturing the screen:

```bash
python3 tools/dlna_mirror.py --tv 192.168.1.103 \
  --bind 192.168.1.102 --port 8090 --source test --play --duration 180
```

This starts a separate temporary HTTP stream, a moving test pattern and a
440 Hz tone using FFmpeg. It does not restart or alter the existing port-80
installation server. The test stops after three minutes; press Ctrl+C to stop
it and its playback on the TV earlier.
If the TV requests byte ranges, the tool reports HTTP 416: a live stream
cannot offer ranges without buffering. A 200 response or a renderer's Play
acknowledgment is **not** evidence of visible video or audible sound.

Only after confirming the live pattern on the TV, run screen capture:

```bash
python3 tools/dlna_mirror.py --tv 192.168.1.103 \
  --bind 192.168.1.102 --port 8090 --source screen \
  --allow-screen-recording --system-audio --play --duration 180
```

macOS may request Screen Recording/System Audio Recording permission for the
terminal, FFmpeg or the temporary Swift helper; grant it only if you want to
share your desktop and Mac sound with the TV. Capture starts only when the
selected TV requests the stream. Video uses the AVFoundation input named
`Capture screen 0`, not a numeric camera index; audio uses ScreenCaptureKit's
system output, **not** the microphone or a third-party audio driver. With
`--system-audio` omitted, the screen stream instead contains silent AAC and
prints a warning. Multiple monitors may require a different `--screen-index`.
The stream stops after three minutes or when you press Ctrl+C; it does not
depend on the port-80 widget installation server.

### Live mirroring latency on this TV

The user reported a large delay while viewing the Mac screen on the TV.
The FFmpeg capture's elapsed time stayed about 19 seconds ahead of the TV's
DLNA playback clock over repeated measurements; LAN round-trip time was
2-8 ms and capture CPU utilization did not indicate a growing backlog.
Padding the MPEG-TS to about 4 Mbps, instead of the normal roughly 1 Mbps,
did not help: the TV's clock was still 20-21 seconds behind. That experiment
was removed rather than left enabled without a demonstrated benefit.
These process/renderer clock comparisons are approximate, not a direct
measurement of photons on the TV panel. The TV's DLNA renderer does not expose
a playback-buffer control in this tool; reducing the encoder's buffering
cannot eliminate a renderer delay of this size. For low-delay screen **and
audio**, use a USB-C-to-HDMI adapter or cable from the Mac to the TV. A
compatible external AirPlay receiver on the TV's HDMI input is a wireless
alternative; this Samsung model does not advertise AirPlay itself.

The stream is unencrypted HTTP on the private LAN, served only to the selected
TV's IP through a random one-time URL. Do not forward port 8090 on the router,
share the URL or display sensitive material. macOS firewall or network
isolation may prevent TV access. Visible playback, stability, latency and
picture/sound on this TV still require direct observation. Protected video
services may show a black image and are not the goal of this tool; use their
existing TV apps instead.

On a Mac that explicitly permits a local screen/audio check, run
`ORSAY_TEST_CAPTURE=1 python3 -m unittest tests.test_dlna_mirror.AuthorizedCaptureTests`.
This checks decoded desktop pixels, a briefly generated 440 Hz system tone,
H.264/AAC tracks, timestamp alignment and process cleanup. It does not save
captured screen or audio, contact the TV or prove that the TV displays it.

## UN40FH5303 network observations (2026-10-25)

With the user's permission to change TV playback and capture the Mac screen:

- The finite 30-second MP4 was requested through DLNA; `GetTransportInfo`
  reported `PLAYING` and `GetPositionInfo` advanced from 0 to 20 seconds.
- The synthetic live MPEG-TS was requested over HTTP by `192.168.1.103`;
  the TV reported `PLAYING`, and its playback position advanced from 3 to
  13 seconds.
- The real `Capture screen 0` FFmpeg source produced a stream requested by
  the TV; it reported `PLAYING` and advanced from 4 to 21 seconds. After an
  input-format and shutdown adjustment, a second screen run advanced to
  7 seconds and exited cleanly.
- A separate one-frame capture checked only aggregate luminance, with no
  image saved or displayed; the frame was nonblack and nonuniform.
- A follow-up screen run automatically stopped after 180 seconds. The TV had
  reported `PLAYING` during that run, then `STOPPED` after cleanup. Nobody
  confirmed what appeared on the panel while it was running.
- A later, bounded live pattern-and-tone test reached `PLAYING`, but no
  observer was available to confirm its image or sound; it was stopped early.
  The TV again reported `STOPPED`, port 8090 closed and no screen capture
  process remained. The existing installation server was not changed.
- The old Mac-screen encoder produced uniform gray in local decoded MPEG-TS
  despite the capture source supplying nonuniform frames. Removing its
  average-bitrate and VBV caps fixed the gray frames beyond the first second;
  the local HTTP test checks nonuniform pixels in the last two seconds.
  The same authorized local test captured a generated 440 Hz tone via
  ScreenCaptureKit and decoded it as AAC along with nonuniform H.264 video.
  The audio/video packet timestamps were aligned; no screen or sound was saved.
- At the next preflight, `192.168.1.103` did not respond to ping, its previously
  reachable service, or SSDP. No corrected video or audio was sent then.
- When the TV returned, it requested the corrected Mac screen/system-audio
  stream with HTTP HEAD and GET 200, reported `PLAYING`, and advanced to
  25 seconds while six short 440 Hz tones played on the Mac. The user was
  unavailable to confirm what the TV displayed or played. The test was
  stopped early; the TV reported `STOPPED`, the temporary HTTP port closed,
  and no FFmpeg or ScreenCaptureKit process remained.

Earlier TV state changes are transport **signals**, not visual or audible
confirmation. The gray report arrived after the original stream stopped, but
the local gray-frame regression was real and has been addressed. Repeat the
bounded test with someone watching and listening to the TV *while it is
active* before calling the feature usable. Local system-audio capture does
not establish that the UN40FH5303 plays its AAC track.

If the TV shows a black screen or drops the live stream, do not treat its
transport status as proof of compatibility. A [free trial of AirBeamTV](https://www.airbeam.tv/mirror-your-mac-screen/samsung/)
is another wireless hypothesis for 2012+ Samsung sets, but it is a third-party
Mac app requiring installation and screen-capture permission. A USB-C/HDMI
adapter and HDMI cable are the more predictable wired alternative.
